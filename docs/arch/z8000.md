# Z8000

Part of [Development style](../development-style.md): read General first.

## CP/M-8000 on the Z8002 **[code]**

`samples/z8002/cpm8000bios.inc` is a CP/M-8000 BIOS on the Z80's
USART and the sector disk, both polled, byte I/O at 16-bit ports;
`cpm8000bios.asm` builds it for DRI's 1.1 kernel:

- The kernel is DRI's binary, `CPMSYS.REL`, the CCP and BDOS linked as
  one relocatable x.out object, with the C runtime it needs from
  `LIBCPM.A`. `debugger/z8000/tools/xout-link.py` links them at a fixed
  address and writes Intel HEX and a symbol include; no Z8000 toolchain
  is needed. An undefined symbol with a size is a C common, allocated
  after the bss.
- DRI shipped the kernel for the Olivetti M20's Z8001, where traps run
  segmented: its BDOS entry and exception handlers read the trap frame at
  segmented offsets, take a 4-byte return address, dereference a
  segment:offset pair and toggle FCW bit 15. `cpm8000glue.asm` holds the
  Z8002 forms of those routines, after the Kontron Z8002 sources of
  P-CP/M-Z8K 1.3, and the link writes them over the kernel's with
  `--patch`; `--keep` fails the link if a patch reaches the next routine
  the kernel still uses.
- The trap frame is DRI's Z8002 one, `cpm8000.inc`'s: R0-R14, the
  normal R15, then the SC identifier, FCW and PC the CPU pushed; a
  handler is called with a 2-byte return address on top. Each trap
  pushes its number, saves R0-R14 below it and swaps it for the normal
  R15. The context block the CCP starts a program with has R0-R15, a
  word, the FCW at 34 and a long PC at 36.
- The trap return reloads R0-R14 from the frame, so a handler's result
  goes into the frame (`FR_R6+CO(r15)`), not just RR6: SC #1 once
  returned map_adr's segments in registers only, every segment address
  came out 0, and split programs loaded into the system's 64K.
- A program is linked at 0 and the loader moves nothing, so the TPA runs
  from 0 and a program load overwrites the reset vector at 0004H. `L`
  the system again before `R`. The PSA sits in the BIOS, at `PSA`.
- The loader takes the TPA for a whole 64K segment: the base page goes
  at FE00H and the program's stack below FD00H whatever the memory region
  table says, which only sizes the program. So the BIOS sits below the
  kernel, the system stack between them, and the memory above the kernel
  is the program's stack. A program's heap, `brk`, is checked against its
  stack only, so one that takes much memory runs into the kernel.
- Three memory regions: the merged TPA below the BIOS, and a code and a
  data segment, each 64K, for a split instruction and data program: ED,
  the DRI compiler passes, assembler and linker. The debugger
  synthesizes the segments, which a Z8002 does not drive: with the split
  I/D device's routing on, a normal-mode cycle goes to the code or data
  segment by its status, and a system-mode one to the system's 64K.
  `xfer` turns the routing on for a split program.
- The memory management call, SC #1, gives an address as segment << 16
  | offset: the system's 0, a split program's 1 for code and 2 for data.
  It copies across segments with the device's copy port; the disk's DMA
  reaches only the system's 64K, so a split program's sectors go through
  a buffer. The BDOS entry gives a program's parameter its data segment,
  as Kontron's left commented out. The kernel's DPH and DPB carry
  16-bit pointers, as the non-segmented C compiler lays them out.
- SELDSK reads the selected drive's format back from DRIVE, bits 4-7,
  and sets its DPH's XLT and DPB: the 8" disk, or hd8 with no skew.
- The kernel's `_initexc` points exceptions 2-23 and 36-47 at its own
  handler through BIOS function 22; the BIOS points SC #1 and SC #3 at
  itself, and the extended instruction trap at a handler that skips the
  instruction: the C start-up clears the Z8070's registers with extended
  instructions, which the M20's BIOS emulated. The trap identifier is the
  instruction's first word, and its mode bits give the length.
